# Задание 4. Передача ставок в кол-центр — ADR + список задач + RoadMap

### **Название задачи:** Предоставление актуальных депозитных ставок операторам банковского и партнёрского кол-центров (MVP)

### **Автор:** Команда цифровой трансформации розничного бизнеса

### **Дата:** 2026-10-16

---

## Контекст
После запуска маркетинговой кампании количество звонков в кол-центр вырастет. Пожилые клиенты (основной сегмент) захотят уточнить условия открытия депозита по телефону. Нужно:
1. Дать операторам **банковского** кол-центра доступ к актуальным ставкам по депозитам.
2. Подключить **партнёрский** кол-центр (внешняя система) для разгрузки; его операторы также должны видеть актуальные ставки. Партнёр готов получать ставки **только в виде файлов** (API-вызовы, например через SFTP, невозможны).

Решение строится на основе текущего процесса работы со ставками (Excel + e-mail) и архитектуры MVP из задания 3 (централизованный сервис ставок в АБС).

## Нефункциональные требования

|**№**|**Требование**|

| 1 | Ставки, отображаемые операторам кол-центра, должны быть актуальными (допустимая задержка обновления — согласуется с бизнесом; для партнёра — периодичность экспорта файла). |
| 2 | Передача файла партнёру должна быть надёжной и аудируемой (журнал публикаций/загрузок). |

## Решение

### Диаграммы C4
- **Диаграмма контекста:** `task4_c4_context.puml` — система «Передача ставок в кол-центры» во взаимодействии с акторами и внешними системами.
- **Диаграмма компонентов:** `task4_c4_components.puml` — компоненты решения и интеграции (сервис ставок, экспорт, файловый шлюз, кол-центры).

### Основные компоненты решения
1. **Сервис ставок по депозитам** (модуль в АБС / Oracle, из задания 3) — единый источник актуальных ставок. Теперь дополнительно обслуживает запросы от кол-центра и экспорт для партнёра.
2. **API ставок для кол-центра** (новый, .NET или расширение системы кол-центра) — предоставляет системе банковского кол-центра актуальные ставки для отображения операторам. Читает из сервиса ставок (через кэш для производительности).
3. **Сервис экспорта ставок** (новый, .NET) — формирует файл с актуальными ставками (CSV/XML) по расписанию и/или при изменении ставок. Публикует файл во файловый шлюз. Работает асинхронно, не нагружая БД АБС напрямую.
4. **Файловый шлюз обмена** (SFTP-совместимое хранилище / согласованное место) — точка передачи файла партнёру. Партнёр загружает файл по своему расписанию.
5. **Система банковского кол-центра** (React.js / Java Spring Boot / PostgreSQL) — отображает ставки операторам через API ставок.
6. **Система партнёрского кол-центра** (внешняя) — загружает файл ставок и использует его для консультирования.

### Интеграции
| Откуда | Куда | Характер | Обоснование |
|--------|------|----------|-------------|
| Сервис ставок (АБС) | API ставок для кол-центра | Чтение через кэш | Актуальные ставки для операторов банка (UC1). |
| API ставок | Система банковского кол-центра | HTTPS API | Отображение ставок в интерфейсе оператора. |
| Сервис ставок (АБС) | Сервис экспорта | Чтение (асинхронно, из кэша) | Формирование файла без нагрузки на БД (NFR4). |
| Сервис экспорта | Файловый шлюз | Публикация файла (CSV/XML) | Передача партнёру в виде файла (UC2). |
| Файловый шлюз | Партнёрский кол-центр | Загрузка файла партнёром | Внешний обмен только файлами (ограничение задачи). |

### Логика принятия решений
1. **Опора на централизованный сервис ставок из задания 3.** Ставки уже выносятся из Excel в АБС; для кол-центра достаточно добавить два потребителя этого источника: API (для банка) и экспорт файла (для партнёра). Это минимизирует дублирование данных.
2. **API для банковского кол-центра, а не файл.** Кол-центр банка — внутренняя система на инфраструктуре банка; API даёт актуальные данные в реальном времени и проще в поддержке, чем периодические файлы.
3. **Файл для партнёрского кол-центра.** Задача прямо указывает: партнёр готов получать ставки только файлами, API (в т.ч. SFTP-вызовы) невозможны. Поэтому выбран экспорт файла во файловый шлюз.
4. **Асинхронный экспорт из кэша.** Чтобы не нагружать перегруженную БД АБС, файл формируется из кэша/сервиса ставок асинхронно по расписанию или по событию изменения ставки.
5. **Триггеры обновления файла.** Файл обновляется при изменении ставки (событие) и/или по расписанию — обеспечивает актуальность в пределах согласованной задержки.

## Альтернативы

1. **API-интеграция с партнёрским кол-центром.**
   - *Почему отклонено:* Задача прямо запрещает API-вызовы (в т.ч. через SFTP) для партнёра; партнёр готов только к файлам.
2. **Передача ставок партнёру по e-mail (как сейчас с Excel).**
   - *Почему отклонено:* Ненадёжно, не аудируемо, нет контроля целостности и актуальности; ручная передача. Файловый шлюз надёжнее и автоматизирует процесс.
3. **Хранение копий ставок в БД кол-центра с ручной синхронизацией.**
   - *Почему отклонено:* Дублирование источника истины, риск рассинхронизации; нарушает принцип единого источника (сервис ставок в АБС).
4. **Один и тот же механизм (файл) и для банковского, и для партнёрского кол-центра.**
   - *Почему отклонено:* Для внутреннего кол-центра API даёт более актуальные данные и проще; файл оправдан только для внешнего партнёра из-за его ограничений.

---

## Недостатки, ограничения, риски

1. **Задержка актуальности ставок у партнёра.** Файл обновляется по расписанию/событию — оператор партнёрского кол-центра может видеть ставку с задержкой. Митигация: сокращение периода экспорта + триггер по изменению ставки; согласование допустимой задержки с бизнесом.
2. **Надёжность обмена файлом.** Если партнёр не загрузил файл вовремя, данные устареют. Митигация: журнал публикаций/загрузок, алерты при отсутствии загрузки, повторная публикация.
3. **Безопасность внешнего обмена.** Файл передаётся во внешнюю систему — необходимы шифрование канала и контроль доступа. Файл должен содержать только справочные ставки (без ПДн).
4. **Нагрузка на сервис ставок.** Добавление двух новых потребителей (API + экспорт) увеличивает нагрузку на сервис ставок. Митигация: кэширование, асинхронный экспорт, мониторинг.
5. **Зависимость от расписания партнёра.** Периодичность загрузки файла партнёром определяется внешней стороной — банк не контролирует момент обновления данных у партнёра.

## Список крупных задач для каждой системы (для планирования)

### АБС (команда АБС, 20 чел.)
- **A1.** Расширить сервис ставок: добавить чтение для внешних потребителей (API кол-центра, экспорт).
- **A2.** Реализовать событие «изменение ставки» для триггера экспорта и инвалидации кэшей.
- **A3.** Обеспечить асинхронный доступ к ставкам без прямой нагрузки на БД Oracle (кэш/прослойка).

### Система банковского кол-центра (подрядчик кол-центра + Java-специалисты банка)
- **C1.** Интеграция с API ставок: получение актуальных депозитных ставок.
- **C2.** Экран/панель для оператора с отображением актуальных ставок по депозитам.
- **C3.** Кэширование ставок на стороне кол-центра (производительность, устойчивость к сбоям API).

### Новый сервис экспорта ставок (команда цифровой трансформации / .NET)
- **E1.** Реализация сервиса экспорта: формирование файла ставок (CSV/XML).
- **E2.** Публикация файла во файловый шлюз по расписанию и по событию изменения ставки.
- **E3.** Журнал публикаций/загрузок, алерты при отсутствии загрузки партнёром.

### Файловый шлюз обмена (IT-отдел)
- **F1.** Развёртывание/настройка SFTP-совместимого файлового шлюза для обмена с партнёром.
- **F2.** Настройка шифрования канала и контроля доступа.
- **F3.** Согласование формата файла и расписания с партнёрским кол-центром.

### Партнёрский кол-центр (внешняя сторона)
- **P1.** Загрузка файла ставок по согласованному расписанию.
- **P2.** Отображение актуальных ставок операторам партнёрского кол-центра.
- **P3.** Обратная связь о загрузке файлов (для аудита).

### Интернет-банк / Сайт (из задания 3, смежные)
- **I1.** Инвалидация кэшей ставок при изменении ставки (единый механизм для всех потребителей).
