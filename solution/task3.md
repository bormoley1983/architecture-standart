# Задание 3. Открытие депозитов онлайн (MVP) — ADR

### **Название задачи:** Концептуальная архитектура MVP открытия депозитов/накопительных счетов в интернет-банке и на сайте

### **Автор:** Команда цифровой трансформации розничного бизнеса

### **Дата:** 2026-10-16

---

## Функциональные требования (Use Cases)

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Клиент (новый), Сайт | Подача заявки на депозит с сайта | 1. Клиент открывает сайт, видит список доступных депозитов с актуальными ставками.<br>2. Выбирает депозит, вводит номер телефона и Ф.И.О., отправляет заявку.<br>3. Сайт шифрует трафик (TLS) и передаёт заявку в сервис обработки заявок.<br>4. Сервис сохраняет заявку и передаёт её в систему кол-центра.<br>5. Менеджер кол-центра получает уведомление о новой заявке. |
| 2 | Оператор кол-центра, Система кол-центра | Обработка заявки с сайта | 1. Менеджер изучает заявку в системе кол-центра.<br>2. При необходимости предлагает особые условия.<br>3. Информирует клиента, что для открытия депозита нужно прийти в отделение для идентификации (банки не принимают новых клиентов без личной проверки документов). |
| 3 | Клиент (существующий), Интернет-банк | Подача заявки на депозит в интернет-банке | 1. Клиент входит в интернет-банк, видит список депозитов с актуальными и персонализированными ставками.<br>2. Выбирает депозит, указывает счёт и сумму.<br>3. Отправляет заявку; система запрашивает СМС-код для подтверждения.<br>4. Клиент вводит СМС-код; операция подтверждена.<br>5. Интернет-банк передаёт заявку в сервис обработки заявок (асинхронно, через очередь). |
| 4 | Менеджер бэк-офиса, АБС | Обработка заявки (MVP) | 1. Сервис обработки заявок передаёт заявку в АБС.<br>2. Менеджер бэк-офиса обрабатывает заявку по существующему процессу: определяет/согласовывает ставку (при необходимости обращаясь в кредитование).<br>3. Менеджер подтверждает условия депозита в АБС.<br>4. АБС фиксирует ставку и статус заявки. |

| 6 | Система, Клиент | СМС-уведомление об открытии депозита | 1. После открытия депозита (в отделении или автоматически) сервис уведомлений отправляет клиенту СМС.<br>2. Клиент получает СМС об успешном открытии депозита. |

## Нефункциональные требования

|**№**|**Требование**|
| :-: | :- |
| 1 | Все сервисы работают 24/7, доступность 99,9%. |
| 2 | Избегать прямой работы интернет-банка с API/БД АБС в новом процессе (БД АБС перегружена). |
| 3 | При сбоях ЦОД сервисы интернет-банка остаются доступными; предусмотрен резервный ЦОД и механизм failover. |
| 4 | Равномерное горизонтальное масштабирование и балансировка нагрузки между серверами, приложениями и ЦОД. АБС масштабируется только вертикально — нагрузку на неё сглаживать. |
| 5 | Шифрование трафика (TLS) при передаче данных с сайта и в интернет-банке. |
| 6 | Отклик по операциям — миллисекунды; исправить загрузку справочных данных >1с (кэширование). |
| 7 | Использовать существующие технологии банка (MS SQL, Oracle, .NET, Java, PHP); новые технологии — совместимые и с внутренней экспертизой. |
| 8 | Очереди сообщений — Kafka на перспективу; текущая платформа интернет-банка несовместима с Kafka. |
| 9 | Функционал СМС в ядре (подрядчик) не дорабатывать; бизнес-логику СМС реализовать силами команды банка. |
| 10 | Разработать документацию для дальнейшего расширения системы. |

## Решение

### Диаграммы C4
- **Диаграмма контекста (C4 Level 1):** `task3_c4_context.puml` — показывает систему «Онлайн-открытие депозитов (MVP)» во взаимодействии с внешними акторами и системами.
- **Диаграмма контейнеров (C4 Level 2):** `task3_c4_containers.puml` — детализирует интернет-банк и АБС, показывает внутренние контейнеры и интеграции.

### Основные компоненты решения

1. **Сайт банка** (PHP + React.js) — фронтенд подачи заявки новым клиентом. Передаёт заявку (телефон, Ф.И.О.) по TLS в сервис обработки заявок.
2. **Интернет-банк** (ASP.NET MVC 4.5 / .NET FW 4.5 / MS SQL) — фронтенд подачи заявки существующим клиентом с персонализированными ставками и подтверждением СМС-кодом. В рамках MVP выделен **депозитный модуль**, который взаимодействует с сервисом обработки заявок асинхронно (через очередь), а не напрямую с АБС.
3. **Сервис обработки депозитных заявок** (новый, .NET) — единая точка приёма заявок с сайта и интернет-банка. Валидирует заявку, сохраняет в MS SQL, публикует событие в очередь сообщений. Изолирует источники заявок от АБС.
4. **Очередь сообщений** (Kafka на перспективу; для MVP — совместимая с платформой банка очередь) — буферизует заявки между сервисом обработки и АБС, сглаживая нагрузку на перегруженную БД АБС.
5. **Сервис ставок по депозитам** (новый модуль в АБС / Oracle) — централизованное хранилище актуальных и персонализированных ставок. Заменяет Excel + e-mail. Доступен бэк-офису депозитов, бэк-офису кредитов и (через кэш) интернет-банку/сайту для отображения.
6. **АБС** (Delphi / Oracle / PL-SQL) — основная система: учёт операций, бухгалтерия, подтверждение условий депозита менеджером бэк-офиса. Получает заявки из очереди, фиксирует ставку и статус.
7. **Сервис уведомлений (СМС)** (новый, .NET) — бизнес-логика СМС на стороне банка (не в ядре платформы). Подписан на события «ставка подтверждена» и «депозит открыт», отправляет СМС через существующий СМС-шлюз → телеком-оператор.
8. **Система кол-центра** (React.js / Java Spring Boot / PostgreSQL) — принимает заявки с сайта, менеджер консультирует клиента.
9. **СМС-шлюз / Телеком-оператор** — существующий канал отправки СМС.

### Интеграции
| Откуда | Куда | Характер | Обоснование |
|--------|------|----------|-------------|
| Сайт | Сервис обработки заявок | HTTPS/TLS, синхронный API | Передача заявки нового клиента (F1, R5). |
| Интернет-банк | Сервис обработки заявок | Асинхронно через очередь | Изоляция от АБС, сглаживание нагрузки (R2, R4). |
| Сервис обработки заявок | Очередь сообщений | Публикация события | Буферизация (R2). |
| Очередь сообщений | АБС | Подписка/потребление | Подача заявки бэк-офису без пиковой нагрузки (R2, +R3). |
| Сервис ставок (АБС) | Интернет-банк / Сайт | Чтение через кэш | Актуальные и персонализированные ставки с откликом в мс (F2, P1, P2). |
| АБС | Сервис уведомлений | Событие «ставка подтверждена» / «депозит открыт» | Триггеры СМС (F6). |
| Сервис уведомлений | СМС-шлюз → Телеком | Существующий канал | Отправка СМС клиенту (F3, F6, +R1). |
| Сервис обработки заявок | Система кол-центра | API | Передача заявки с сайта менеджеру (F7). |

### Логика принятия решений и выбора технологий
1. **Централизация ставок в АБС** — ставки сейчас только в Excel; бэк-офис депозитов и кредитов должны работать с ними совместно. АБС уже является основной системой учёта, а команда АБС владеет Oracle/PL-SQL (S1, S2). Это устраняет ручную передачу по e-mail и даёт единый источник истины для персонализации ставок в интернет-банке.
2. **Асинхронная интеграция через очередь** — прямое подключение интернет-банка к БД АБС недопустимо (R2, перегрузка БД). Очередь буферизует заявки и сглаживает нагрузку на вертикально масштабируемую АБС (+R3). Kafka выбрана «на перспективу» (S3), но т.к. текущая платформа интернет-банка несовместима с Kafka (+R2), для MVP используется очередь, совместимая с платформой банка; миграция на Kafka — часть эволюции к микросервисной архитектуре (S5).
3. **Выделение депозитного модуля в интернет-банке** — полный перевод монолита на микросервисы вне scope MVP (S5). Выделяем только депозитный функционал, чтобы не трогать ядро платформы и не зависеть от подрядчика для обновления ядра.
4. **СМС на стороне банка** — функционал СМС в ядре требует доработки подрядчика (+R1), чего избегаем. Сервис уведомлений реализует бизнес-логику (какие события триггерят СМС) силами команды банка, используя существующий СМС-шлюз.
5. **Кэширование ставок** — для отклика в миллисекунды (P1) и исправления проблемы загрузки справочников >1с (P2) ставки кэшируются на стороне интернет-банка/сайта с периодическим обновлением из сервиса ставок.
6. **Бесштатность и балансировка** — сервисы MVP спроектированы stateless для горизонтального масштабирования и failover между ЦОД (R3, R4).

## Альтернативы

1. **Прямая интеграция интернет-банка с АБС через API.**
   - *Почему отклонено:* БД АБС перегружена, прямые синхронные вызовы ставят под угрозу работоспособность банка (R2). Нет изоляции нагрузки.
2. **Полный перевод интернет-банка на микросервисную архитектуру.**
   - *Почему отклонено:* Вне scope MVP (S5 — только в рамках задачи открытия депозитов). Высокая стоимость и риск; текущая платформа несовместима с Kafka (+R2).
3. **Хранение ставок в отдельной новой БД (не Oracle).**
   - *Почему отклонено:* Нарушает требование использовать существующие технологии и экспертизу банка (S1, S2, +R5). Oracle уже есть в АБС.
4. **Доработка ядра платформы интернет-банка для СМС силами подрядчика.**
   - *Почему отклонено:* Требует участия подрядчика, к которому привязано обновление ядра (+R1); увеличивает стоимость и сроки. Реализация на стороне банка быстрее и независимее.
5. **Синхронная передача заявок с сайта/интернет-банка напрямую в АБС (без очереди).**
   - *Почему отклонено:* Пиковая нагрузка при маркетинговой кампании может перегрузить БД АБС (R2, +R3). Очередь обеспечивает устойчивость.

## Недостатки, ограничения, риски

1. **Несовместимость платформы интернет-банка с Kafka.** Для MVP используется промежуточная очередь; миграция на Kafka отложена. Риск: технический долг, необходимость повторной работы при переходе на микросервисы.
2. **Зависимость от АБС как единой точки подтверждения.** Менеджер бэк-офиса по-прежнему обрабатывает заявки вручную (MVP). Это не устраняет операционные издержки полностью — цель финального состояния (12 мес.) — автоматизация без бэк-офиса.
3. **Вертикальное масштабирование АБС.** При росте объёма онлайн-заявок АБС может стать узким местом; очередь сглаживает, но не устраняет ограничение (+R3).
4. **Кэширование ставок создаёт риск устаревания данных.** Если ставка изменится в АБС, кэш интернет-банка/сайта обновляется с задержкой. Митигация: короткий TTL кэша + инвалидация по событию изменения ставки.
5. **Офлайн-идентификация нового клиента.** Заявка с сайта не завершает открытие депозита — клиент должен прийти в отделение (R4). Это ограничивает «полную цифровизацию» для новых клиентов на этапе MVP.
6. **Резервирование ЦОД.** Механизм failover между ЦОД существует, но автоматичность переключения и RTO/RPO не заданы в исходнике — требуется уточнение при проектировании инфраструктуры.
7. **Безопасность персональных данных.** Сайт передаёт телефон и Ф.И.О.; помимо TLS (R5) необходимы меры защиты на уровне хранения (маскирование, доступ по ролям), которые выходят за рамки концептуальной архитектуры MVP.
