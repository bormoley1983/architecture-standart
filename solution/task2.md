# Задание 2. FURPS+ таблица требований (MVP: заявка на депозит в интернет-банке и на сайте)

Обобщение всех требований, полученных от бизнеса и IT-команд, в формате FURPS+.
Архитектурно значимые требования помечены **⬆**.

| Код | Требования | Комментарий |
|-----|------------|-------------|
| **F** | **Функциональные (Functionality)** | |
| F1 ⬆ | На сайте новый клиент видит список доступных депозитов с актуальными ставками и может подать заявку, оставив номер телефона и Ф.И.О. | Сайт — PHP + React.js. После заявки менеджер кол-центра связывается с клиентом. |
| F2 ⬆ | В интернет-банке клиент видит список доступных депозитов с актуальными и **персонализированными** ставками; указав счёт и сумму, подаёт заявку на открытие депозита. | Персонализация ставок требует доступа к данным клиента — источник ставок должен быть централизованным (см. R-требования). |
| F3 ⬆ | Операция открытия депозита в интернет-банке подтверждается **СМС-кодом**. | Функционал СМС сейчас в ядре системы (подрядчик). Доработку ядра лучше избежать — бизнес-функционал СМС реализовать силами команды банка. |
| F4 ⬆ | Ставки по депозитам должны храниться в едином месте и быть доступны сотрудникам бэк-офиса депозитов **и** бэк-офиса кредитов. Сейчас ставки только в XLS. | Кандидат на реализацию — АБС (как и весь процесс согласования ставки). Устраняет ручную передачу Excel по e-mail. |
| F5 ⬆ | В MVP заявку на открытие депозита обрабатывает менеджер бэк-офиса: он подтверждает условия депозита в АБС. | Промежуточное состояние (6 мес.): бэк-офис работает по старому процессу, но данные уже централизованы. |
| F6 ⬆ | Клиент получает **СМС-уведомления** после подтверждения размера ставки и после открытия депозита. | Два триггера СМС: подтверждение ставки + открытие депозита. |
| F7 | Менеджер кол-центра, изучив заявку в системе кол-центра, может предложить особые условия. | Заявка с сайта попадает в систему кол-центра; менеджер видит её и консультирует. |
| **U** | **Удобство использования (Usability)** | |
| U1 ⬆ | Интерфейс работы должен быть максимально удобным для клиента. | Ключевой фактор привлечения молодой аудитории — целевой сегмент трансформации. |
| U2 ⬆ | Соблюдение корпоративной системы дизайна: привычные цвета и брендированные элементы во всех приложениях. | Единый дизайн-код для сайта, интернет-банка и новых экранов. |
| U3 | После подачи заявки на сайте клиенту звонит менеджер кол-центра (минимизация числа действий клиента). | Снижает барьер для нового клиента, который ещё не идентифицирован. |
| **R** | **Надёжность (Reliability)** | |
| R1 ⬆ | Все сервисы должны работать **24/7** и быть доступны в **99,9%** случаев. | Архитектурно значимо: определяет требования к отказоустойчивости и резервированию. |
| R2 ⬆ | Избежать прямой работы интернет-банка с API АБС в новом процессе (БД АБС уже перегружена; онлайн-заявки по многим продуктам могут поставить под угрозу работоспособность банка). | Требует буферизации/асинхронизации между интернет-банком и АБС (очередь сообщений / промежуточный сервис). |
| R3 ⬆ | При сбоях в ЦОД сервисы интернет-банка должны оставаться доступными и выдерживать требуемую нагрузку. | Сейчас всё в одном ЦОД на одной группе серверов; есть резервный ЦОД для переключения. Требуется механизм failover. |
| R4 ⬆ | Предусмотреть **равномерное горизонтальное масштабирование** и распределение запросов между серверами, приложениями и ЦОД (балансировка нагрузки). | АБС масштабируется только вертикально — поэтому нагрузку на неё нужно сглаживать. |
| R5 ⬆ | Передача чувствительной информации с сайта защищается **механизмом шифрования трафика**. | Сайт передаёт персональные данные (телефон, Ф.И.О.) — обязателен TLS. |
| R6 ⬆ | Данные в интернет-банке при передаче также должны быть защищены механизмом шифрования. | Аналогично R5 для канала клиент ↔ интернет-банк. |
| **P** | **Производительность (Performance)** | |
| P1 ⬆ | Отклик по всем операциям должен быть максимально быстрым — в **миллисекундах**. | Бизнес ожидает суб-секундный отклик на пользовательские операции. |
| P2 ⬆ | Исправить проблему: при проведении платежей некоторые справочные данные загружаются **больше секунды**. | Известный дефект производительности; целевое состояние — загрузка справочников в пределах миллисекунд (кэширование). |
| **S** | **Поддерживаемость (Supportability)** | |
| S1 ⬆ | При доработках во всех системах максимально использовать уже имеющиеся в банке технологии (например, БД MS SQL и Oracle). | Снижает стоимость внедрения и риск; новые технологии должны быть совместимы с существующими платформами разработки. |
| S2 ⬆ | Желательно, чтобы внутри банка уже была экспертиза по новым технологиям (сотрудники понимают их хотя бы на уровне языков программирования). | Ограничивает выбор технологий стеком, известным командам (.NET, Java, PHP, PL-SQL). |
| S3 ⬆ | Если нужны очереди сообщений — использовать **Kafka** на перспективу. | Учёт: текущая версия платформы интернет-банка несовместима с Kafka (см. ограничения). |
| S4 ⬆ | Предусмотреть разработку **документации** для дальнейшего расширения системы. | Поддержка эволюции MVP → финального состояния (12 мес.) и подключения кредитования. |
| S5 | Возможно, стоит подумать о переводе интернет-банка на микросервисную архитектуру, но пока только в рамках задачи открытия депозитов. | Ограниченный scope: не полный рефакторинг монолита, а выделение депозитного функционала. |
| **+R** | **+ Ограничения (Restrictions)** | |
| +R1 ⬆ | Функционал работы с СМС реализован в ядре системы интернет-банка и требует доработки подрядчика — этого лучше избежать; бизнес-функционал СМС реализовать силами команды банка. | Ограничивает подход: не трогать ядро, обвязать СМС на уровне приложения/сервиса банка. |
| +R2 ⬆ | Текущая версия платформы интернет-банка **несовместима с Kafka**. | Прямое ограничение на использование Kafka в существующем монолите без модернизации платформы. |
| +R3 ⬆ | АБС может масштабироваться **только вертикально** из-за своей базы данных (Oracle). | Нельзя горизонтально масштабировать АБС — нагрузку на неё нужно ограничивать и сглаживать. |
| +R4 ⬆ | Банки не могут принимать новых клиентов без личной проверки документов: после звонка новому клиенту надо прийти в отделение для идентификации. | Бизнес-ограничение регуляторики: онлайн-заявка с сайта ≠ полное открытие, требуется офлайн-идентификация. |
| +R5 ⬆ | Новые технологии должны быть совместимы с существующими платформами разработки банка. | Ограничивает выбор фреймворков/инфраструктуры экосистемой банка (.NET Framework, MS SQL, Oracle). |

## Легенда
- **⬆** — архитектурно значимое требование (влияет на выбор архитектуры, технологий, границ компонентов и интеграций).
- Остальные требования важны для реализации, но не определяют архитектуру напрямую.
